## What this is

A zero-dependency, single-page NixOS configuration editor. No build step, no framework, no package manager. `bin/server.py` serves the app and edits the `*.json` config files under a directory given via `--file`, discovered recursively (except `custom-options.json`, a schema-extension sidecar, and dotdirs like the default `.ezconf-backups`) — each file an independently editable/saveable/backed-up "file," chosen via a dropdown in the header, merged together only at Nix-eval time via `lib.mkMerge` in `json2nix.nix`. Files can be nested in subfolders (e.g. `services/nginx.json`) purely for organization. `--file` can also name a specific `*.json` file — its directory becomes the working set, and it's preselected initially.

## Running

```sh
python3 bin/server.py                          # reads ezconf.toml in CWD (or --config FILE)
python3 bin/server.py --webroot DIR --file FILE # CLI args override the config file
python3 bin/server.py --generate-cert [DIR]     # self-signed cert for dev use
python3 bin/server.py --generate-ca [DIR]       # local CA + server cert (used by the NixOS service)
nix run .#ezconf -- --file /path/to/configuration.json
```

Python deps (all optional, all in the flake devShell): `python-pam` (PAM auth), `cryptography` (`--generate-cert`/`--generate-ca`), `tomli` (TOML config on Python < 3.11).

Auth: `--auth auto` (default — PAM if available, else custom), `--auth custom` (username/password from config), `--auth pam`. `allowed_users` in config restricts PAM logins and renders a dropdown instead of a free-text username field. Authentication is always required.

Terminal: a separate process, `bin/terminal.py`. Pass `--terminal-port PORT` to `server.py` to enable the panel; run `terminal.py --config ezconf.toml` on the same port.

## Generating data files

`bin/generate-nixos-data.py` generates the JSON files the editor needs; exposed via the flake as `ezconf-mkoptions`:

```sh
ezconf-mkoptions                          # all files → webroot/autocomplete/
TARGET=/path/to/flake ezconf-mkoptions all myhostname
ezconf-mkoptions options   # only options.json
ezconf-mkoptions packages  # only packages.json
ezconf-mkoptions kernels   # only kernels.json
ezconf-mkoptions -v        # verbose nix errors (otherwise a failed nix eval is silent)
```

Shells out to `nix eval --json`; `TARGET` env var sets the flake path (default `/etc/nixos`). Output defaults to `autocomplete/` under CWD (`-o DIR` to override) — it belongs inside WEBROOT so the server can serve it, and is gitignored (user-specific generated data).

When `hostname` is omitted (as both `ezconf.service`'s `preStart` and `/api/v1/autocomplete/update` do — neither passes one), it's not just `hosts[0]`: `socket.gethostname()` is checked against the flake's `nixosConfigurations` first, since `networking.hostName` is what actually becomes the running machine's hostname — this picks the right host automatically on a multi-host flake instead of an arbitrary one. Only falls back to `hosts[0]` if the machine's own hostname isn't one of the flake's hosts (e.g. generating for a different target than the one you're running on).

Every `nix eval` call goes through one `nix_eval()` helper, which adds `--no-allow-import-from-derivation` (this only ever needs declarative metadata, never a build — a third-party module like disko defining a type/default that reads real hardware should fail fast, not hang) and a 600s timeout (`NIX_EVAL_TIMEOUT`), printed as a one-line warning unconditionally on timeout (unlike a normal failure, which needs `-v`). Without the timeout, a hung eval could block `ezconf.service`'s own `preStart` past systemd's startup timeout and fail the whole service.

`nix_eval()` returns `None` on any failure (a distinct value from a legitimately empty result). Every call site that feeds it into `generate_packages()`/`generate_options()`/`generate_kernels()` checks for `None` explicitly and calls `warn()` before falling back to `[]` — a bare `nix_eval(...) or []` was tried first and rejected, since it made a *total* eval failure (e.g. a host's `configuration.nix` importing a `hardware-configuration.nix` that doesn't exist at `TARGET`) silently produce an empty, "successful" output file with no diagnostic at all, indistinguishable from a file that legitimately has zero entries.

`generate_options()` filters out `internal = true` options before touching them (the NixOS convention for "not meant to be set directly," e.g. disko's underscore-prefixed options) and wraps every field (`description`/`type`/`default`/`example`/`required`) in `safeGet()`, which runs `builtins.tryEval (builtins.deepSeq v v)` rather than plain `tryEval (f opt)` — `nix eval --json` has to force every field to serialize the result, and plain `tryEval` only protects against a throw while forcing to shallow WHNF; a value that's itself a nested attrset can pass that check and only throw later when something forces a field inside it. `deepSeq` forces the whole structure up front, inside the guard, so nested throws (e.g. a disko default that reaches into a nonexistent realized `config`) are actually caught instead of aborting the entire options list.

## Server architecture (`bin/server.py`)

Single `ThreadingHTTPServer` bound to `BIND_ADDR:WEB_PORT` (default `127.0.0.1:9090`). `StaticHandler` (subclass of `SimpleHTTPRequestHandler`) serves static assets and handles the API. All endpoints below require auth except `/download-ca`.

**API endpoints**:
- `GET /download-ca` — serves `CA_FILE` as a downloadable PEM, when set
- `GET /api/v1/ping` — `{boot_id, webroot_hash, theme, terminal_enabled, mkoptions_enabled, backup_enabled, nixos_target, buttons}`, polled periodically by the frontend's restart/upgrade detection — see "Restart detection" below
- `GET /api/v1/markdown-files` — `{files}`, every `*.md` file under `NIXOS_TARGET` found by a recursive walk, as relative paths (e.g. `services/nginx/README.md`); dotfiles/dotdirs and symlinks (files and directories) are skipped the same way `_iter_system_export_files()` skips them, so this can't follow a `result`/`result-*` symlink into `/nix/store` or loop on a cycle
- `GET /api/v1/markdown-files/content?name=RELATIVE_PATH` — `{content}` for one of those files; `name` is a relative path under `NIXOS_TARGET` (subpaths allowed, `..`/absolute paths rejected), same shape as `resolve_config_path()`
- `GET /api/v1/files` — `{files, folders, default}`; `folders` lists every subdirectory including empty ones (so an empty folder still shows as a tab group after reload)
- `GET /api/v1/file?file=NAME` — raw JSON content of the resolved config file (falls back to `DEFAULT_FILE`)
- `POST /api/v1/file/save?file=NAME` — writes the file, backing up the previous contents first; creates it if new
- `POST /api/v1/autocomplete/update` — reruns `MKOPTIONS_CMD -v`; only available when `--mkoptions` is set. Exit 0 alone isn't treated as success: `generate-nixos-data.py` can exit 0 while a total eval failure left `options.json`/`packages.json`/`kernels.json` as an empty `[]` (see "Generating data files"), so `_is_empty_json_array()` checks the actual output files in `out_dir` first — any of them coming back empty is treated as a failure even on exit 0. On any failure (empty files, or a genuinely nonzero exit), the full captured stdout+stderr (ANSI-stripped via `_strip_ansi()`) comes back as `error`, so `-v`'s detailed trace is what the frontend shows in a modal (`showMkoptionsOutputModal()`) — a bare success just returns `{"ok":true}` with no popup, since checking real files rather than parsing log text is what lets a clean run stay quiet without needing to filter `generate-nixos-data.py`'s routine `info()` progress lines out of anything
- `GET /api/v1/system-export` — zips the entire `NIXOS_TARGET` tree (not just `CONFIG_DIR`) via `_iter_system_export_files()`; always skips symlinks; skips dotfiles/dotdirs and `hardware-configuration.nix` by default (`SYSTEM_EXPORT_EXCLUDE_DOTFILES`/`SYSTEM_EXPORT_EXCLUDE`, both configurable, since hardware-configuration.nix is machine-specific and shouldn't be bundled into something meant as a template)
- `POST /api/v1/system-import` — writes a zip's files directly into `NIXOS_TARGET`, immediately, no Save step, no undo; validates every entry (rejects path traversal, dotfiles) before writing any of them; overwrites same-named files, never deletes anything the zip doesn't mention. Calls `backup_system()` first (a no-op when disabled) — an import is a destructive overwrite, so this is exactly the moment a "before" snapshot is worth having
- `POST /api/v1/system-backup` — same file selection as `system-export`, but zips into a timestamped file in `SYSTEM_BACKUP_DIR` instead of streaming to the client; not triggered on its own on any schedule (see `backup_system()`), unlike the per-file JSON backups below which happen automatically on every save — but is called automatically by `system-import` and `system-backup/restore`, not just its own endpoint
- `GET /api/v1/system-backups` — lists backups in `SYSTEM_BACKUP_DIR`, newest first
- `POST /api/v1/system-backup/restore?name=NAME` — applies a backup zip already in `SYSTEM_BACKUP_DIR` straight to `NIXOS_TARGET`; shares `_apply_system_zip()` (the actual "write these entries into `NIXOS_TARGET`" logic) and the same auto-backup-first call with `system-import` — the two endpoints differ only in whether the zip bytes come from an upload or a file already on disk
- `GET /api/v1/backups?file=NAME` — lists backups in `BACKUP_DIR` for that file, newest first
- `GET /api/v1/backup/content?name=NAME` — a backup's raw content; read-only, the frontend loads it as an unsaved edit
- `POST /api/v1/file/delete` — deletes a config file; zero files afterward is a valid state
- `POST /api/v1/file/rename` — renames/moves a file (covers moving between folders too); also how a file is disabled/enabled, via renaming to/from `NAME.json.disabled` (`json2nix.nix`'s glob requires an exact `.json` suffix, so no changes needed there)
- `POST /api/v1/folder/create` / `folder/delete` — create (`os.makedirs`) / delete (`shutil.rmtree`, recursive) a subfolder
- `POST /api/v1/folder/disable` / `folder/enable` — renames a folder to/from `.NAME.disabled` (dot-prefixed, so `json2nix.nix` skips it like any dotdir); everything nested moves for free with one rename

**File routing**: `resolve_config_path()` accepts a relative path or its `.disabled` form and keeps writes inside `CONFIG_DIR` (a correctness guard, not a security boundary — an authenticated user already has terminal access). `list_config_files()`/`list_config_folders()` walk `CONFIG_DIR` skipping dotdirs, except a disabled folder (`.NAME.disabled`) is still walked so its files keep listing as disabled tabs. Backup filenames flatten the relative path (`services/nginx.json` → `services--nginx`) so `BACKUP_DIR` stays flat even with nested tabs.

**Disabling a file or folder** is a pure filesystem rename, not a content change — round-trips losslessly, and the disabled file/folder stays fully viewable/editable/saveable, just excluded from the Nix merge. A file: append `.disabled`. A folder: dot-prefix and suffix its own directory name (`services` → `.services.disabled`) — only top-level folders get this in the UI.

**Key globals**:
- `WEBROOT`, `CONFIG_DIR`, `DEFAULT_FILE` — static assets dir, config files dir, preferred initial tab
- `AUTOCOMPLETE_DIR` — override for `/autocomplete/*`; `MKOPTIONS_CMD` — enables the autocomplete/update endpoint
- `NIXOS_TARGET` — flake path for mkoptions and for `system-export`
- `SYSTEM_EXPORT_EXCLUDE_DOTFILES` / `SYSTEM_EXPORT_EXCLUDE` — export exclusion config (defaults: `True` / `{'hardware-configuration.nix'}`)
- `THEME`, `EZCONF_MODE` (`None` or `'install'` — deploy-time only, see "Install mode" below), `TERMINAL_PORT`
- `BIND_ADDR`, `TRUSTED_HOSTS` — CSRF Host-header allowlist for `_valid_host`; `"*"` disables the check entirely (for cases like an installer ISO where the reachable address can't be known ahead of time)
- `CA_FILE`, `BACKUP_DIR`, `BACKUP_COUNT`, `SYSTEM_BACKUP_DIR`, `SYSTEM_BACKUP_COUNT`
- `STATIC_BUTTONS` — deploy-time terminal buttons from `[[buttons]]` in TOML. `services.ezconf.buttons` is one NixOS option either way, so a button set in a `*.json` file becomes a `STATIC_BUTTONS` entry too once saved and rebuilt — `getAllButtons()` avoids showing it twice not by matching the two copies against each other (every attempt at that broke on a rename, since whatever the match relies on is exactly what a rename changes) but by only ever showing a `STATIC_BUTTONS` entry when it's marked `static = true`; a `*.json`-declared button is otherwise read *only* from the file, so there's nothing to reconcile and nothing a rename can desync
- `_SESSION_KEY` — expected `ezconf_session` cookie value
- `BOOT_ID` — fresh random hex every process start, never persisted (unlike `_SESSION_KEY`) — lets the frontend detect a different process is now serving the page
- `WEBROOT_HASH` — SHA-256 of `index.html`/`style.css`/theme CSS files, computed once at startup; only changes across a restart when the frontend itself actually changed (a real package upgrade), unlike `BOOT_ID` which changes on every restart

**Auth flow**: `/login` sets `Set-Cookie: ezconf_session=<SESSION_KEY>; HttpOnly; SameSite=Strict`. `check_auth()` compares that cookie to `_SESSION_KEY`.

**PAM auth**: `check_pam()` creates a fresh `pam.pam()` instance on every call — never use a global instance, it segfaults on Linux after the first `authenticate()` call.

## Terminal service (`bin/terminal.py`)

Separate process, own port (default 9091), WebSocket-upgrades a PTY session. Reads the same `ezconf.toml`. Authenticated via the `ezconf_session` cookie on the upgrade request. Runs as `ezconf-terminal.service`, separate from `ezconf.service`, with `restartIfChanged = false` — it forks shells directly as its own children, so restarting the unit kills whatever's running inside them; a rebuild must never do that automatically.

**Session persistence** (`TERM_PERSIST`, off by default — set by `terminal_persist` in TOML / `terminalPersist` in the NixOS module): when on, the shell survives a dropped/closed WebSocket connection (browser closed, network blip, logout) — it keeps running server-side and a later reconnect reattaches to it, rather than every connection forking a fresh shell that dies the moment that one connection ends. There is only ever one shell (`_SESSION` — a single global, not a dict keyed by any id), shared by every connection regardless of who or what browser it comes from — a per-browser id (generated client-side, kept in `localStorage`) was tried first and reverted: it has a real failure mode a single shared session doesn't, since clearing cookies/site data (which usually wipes `localStorage` too) would silently orphan that browser's still-running shell forever, unreachable by anything, with no cleanup mechanism at all — there's no id to lose in the first place when there's only one session, period. The trade-off is explicit and intentional: anyone who can log in shares this exact one terminal, always — consistent with the rest of ezconf, which has no per-user identity anywhere else either (one shared login for everyone with access, see `check_auth()` in `server.py`). When `TERM_PERSIST` is off, `_terminal_ws()`'s own `finally` (a client disconnecting, with none left attached) clears `_SESSION` synchronously (immune to a race against a fast-following reconnect, e.g. a page reload, that could otherwise land before the shell's own async teardown finishes) and nudges the shell to exit — `_session_reader()` still does the actual process/fd cleanup once it notices, exactly as it would for a shell that exited on its own, just prompted a moment sooner than it otherwise would have been.

**Reattaching to a session with a full-screen program running** (`htop`, `vim`, `top`, ...) needs an explicit nudge to redraw correctly: `connectTerminalWs()`'s `onopen` (index.html) sends a real, briefly-sustained two-step resize on every connect (an off-by-one size, a 150ms pause, then the actual size) rather than a single message straight to the target size. A single resize is a no-op at the kernel level (no `SIGWINCH` delivered at all) whenever it happens to already match the session's last-known size — routinely true reattaching in the same browser window — and even a genuine momentary size change with no pause can be missed if the app's own signal handler doesn't run until after both edges have already landed, observing only the final, unchanged size. Confirmed empirically (with `htop`) that server-side attempts at forcing this alone (an immediate resize wiggle at attach time, and later a version deferred to the first real resize message) both failed to reliably trigger a correct full redraw, while this two-step client-driven version — deliberately mirroring what manually dragging the panel to resize it does, which was confirmed to always work — does. The server's own resize handling stays deliberately simple (`_terminal_ws()`'s `resize` case just applies whatever `rows`/`cols` it's given, no special-casing) — the responsibility for making the resize "real" lives entirely on the client.

`_SESSION` holds the one still-running shell (or `None`), independent of any particular connection — `_create_session()` forks the shell and starts `_session_reader()`, the one thread that owns that shell's entire lifecycle from then on: it keeps draining the PTY (into a bounded `TERM_BUFFER_MAX`-byte buffer, and out live to whichever clients are currently attached) regardless of whether anyone's attached at all, and is the *only* thing that ever tears the session down — and only once the shell process itself actually exits (or its PTY read fails outright), never because a client merely disconnected. `_terminal_ws()`'s own `finally` only ever removes that one connection from the session's `writers` set. Two separate locks: `_SESSION_LOCK` guards `_SESSION` itself (setting/checking/clearing it), the session's own `lock` guards that session's mutable state (`buffer`/`writers`/`rows`/`cols`) — so the session's I/O never blocks a connect/disconnect deciding whether to (re)create it.

A client that (re)connects gets the session's buffered tail replayed first (a snapshot taken atomically with attaching, under the session's lock, so nothing already broadcast live is duplicated and nothing appended after attaching is skipped), then `'ready'` — sent with `READY_DELAY`'s startup-race delay only for a *brand-new* shell; a reused one is long past its own startup, so `'ready'` goes out immediately. The frontend (`_termExited`, index.html) distinguishes "the shell itself exited" from "just a dropped connection" via an explicit `{"type":"exited"}` control message `_session_reader()` sends before closing — not the WebSocket's own `wasClean`, which reflects whether the *connection* closed cleanly and no longer implies anything about whether the *shell* did once a connection drop and a shell death are different events. Only `'exited'` disposes the whole `_term` instance; an ordinary drop just reconnects and keeps whatever's already on screen, with the replayed tail (if anything was missed) appended after it.

None of this survives the `ezconf-terminal.service` process itself dying (a reboot, a manual `systemctl restart`) — `_SESSION` is in-memory only, nothing here is written to disk. A browser reconnecting after that just gets a brand-new shell (`_SESSION` is `None` again) rather than erroring — from the browser's side this looks like an ordinary reconnect (not the `'exited'` signal), so the terminal panel doesn't reset itself, but nothing about cwd/env/foreground jobs actually survived; that's a hard ceiling no in-process persistence scheme can get around.

## Frontend architecture (`webroot/index.html`)

All logic is in one `<script>` block. No modules, no build step.

**Data model**: `config` (active tab's JSON, plain object), `options` (`{path, type, description, default, example}[]`), `packages` (`{name, description}[]`). Two sentinel shapes: `{ _expr: "..." }` (raw Nix expression) and `{ _disabled: true, _value: <original> }` (option disabled in the UI, filtered by `json2nix.nix`, original value preserved for re-enabling).

**Multi-file state**: every file's config lives in `fileConfigs[name]` up front, not just the active one. `config === fileConfigs[activeFile]` always — anything that reassigns `config` wholesale (import, undo/redo, reload) must sync back, which `renderAll()` does unconditionally as a safety net. `fileSaved[name]` is the last-saved-to-disk snapshot; `isAnyDirty()` compares every file against it (plus non-empty `pendingFsOps`). `saveToServer()` POSTs every dirty file. `name` keys are `CONFIG_DIR`-relative paths.

**Live dirty-tracking vs. undo granularity**: scalar field editors call `setAtPath()` on `'input'` (per keystroke), not `'change'` (blur only) — otherwise Save stayed stale until the field lost focus. `_pushHistory()` stays on `'change'` only, so undo still records one entry per edit session, not per character. Nullable-string fields split the same way: the value updates on `'input'`, but swapping the widget itself (plain text ↔ "null" placeholder) is a full `renderAll()` (would steal focus mid-typing), so that stays on `'change'`.

Tab bar: no "+"/"new" buttons anywhere — everything is right-click (blank space → New file/folder; a tab → its own menu; a folder group → New file here/Delete folder). Tabs are `<div>`s not `<button>`s (rename swaps the label for a live `<input>`, invalid inside a real button). Double-click renames inline; dragging (custom mousedown/mousemove implementation, 5px threshold) moves a tab between folders.

**Nothing touches the server until Save** — not just content, but every filesystem-affecting action (delete, rename/move, disable/enable) for both files and folders. `pendingFsOps` is an ordered queue of operation descriptors, replayed in recorded order by `saveToServer()` before any content save, stopping at the first failure. Replaying in order (rather than collapsing into a minimal net op) is what makes a chain of edits to the same file — renamed twice, moved into a folder created moments earlier — replay correctly for free. `folderExists` tracks folders confirmed-or-about-to-be-confirmed on disk, the folder equivalent of `fileSaved`-presence, used to decide whether an op needs to be queued at all (a file/folder never saved has nothing on disk to touch). Delete/rename no longer prompt for confirmation — since nothing is real until Save replays it, a prompt would warn about something that hasn't happened yet.

**Undo/redo** (`globalHistory`/`_pushHistory`/`undo`/`redo`/`_restoreSnapshot`/`_applySnapshot`) is one global stack of full-state snapshots (`files`, `folders`, every `fileConfigs` entry, `fileSaved`, `pendingFsOps`, `folderExists`), not per-file — undoing a delete has to resurrect the file *and* un-queue the disk delete, which a content-only diff can't express. Deduped against the previous snapshot by everything except `activeFile`, so switching tabs doesn't spend its own undo step. Can't undo something Save has already replayed against disk — undoing back across an applied delete resurrects the file locally, but the server has no memory of it.

**Undo/redo survives a reload**: `_schedulePersistHistory()` debounces (400ms) writing `{history, index}` to `localStorage['ezconf-history-v1']`. On load, right after fresh state loads from disk, `_tryRestoreHistoryFromStorage()` searches the persisted stack newest-first for an entry whose content matches that fresh disk state, and resumes there if found — this is what decides safety, not *why* the reload happened (plain reload, hard reload, restart-triggered reload are all just "a reload"). No match (something changed on disk outside this tab's awareness) discards the whole stack rather than resuming into a lineage that no longer describes reality.

**Restart detection** (`BOOT_ID`, `initRestartWatcher()`, `_restartDetected`): `initRestartWatcher()` polls `GET /api/v1/ping` every `POLL_INTERVAL_MS` (5s), comparing the response against what this page actually has — a changed `boot_id` alone isn't "reload now". `STATIC_BUTTONS` differing is patched in place with no reload (the most common actual change); `webroot_hash`/`theme`/`terminal_enabled`/`mkoptions_enabled`/`backup_enabled`/`nixos_target` differing sets `_restartDetected` and reveals `#reload-notification` (hidden otherwise, floats over the top-right corner of `#editor-area` — `.main` is its positioning context, same convention as `.sidebar`/`.markdown-panels`) — `webroot_hash` catches an actual package upgrade. Never reloads on its own, dirty or not: `location.reload()` only ever runs from that element's own `onclick`, so the user picks the moment rather than the page pulling itself out from under an edit in progress. A dead session (401) is just the poll's own response status, no separate check needed. A `visibilitychange` listener polls immediately when the tab becomes visible again, since a background tab's `setInterval` can be throttled to as little as one wake-up per minute after 5+ continuous minutes hidden ("intensive timer throttling").

This used to hold `GET /api/v1/ping-stream` open via `EventSource` instead — near-instant detection (the connection dying the moment the old process exits) rather than up to one poll interval's latency. Reverted after confirming, repeatedly and empirically, that an `EventSource` reconnecting after the process it's connected to restarts reliably wipes the browser's *entire cookie jar for the origin* as a side effect — every subsequent request lost its session, on any port, not just this connection's own. Reproduced in both headless and real windowed Chrome, and with a control that stubbed out `EventSource` entirely (identical restart, cookie stayed completely intact with polling alone) — a real, reproducible Chromium behavior that only a persistent/reconnecting connection type triggers, not something wrong in this code, but one whose fix isn't available from this side without understanding Chromium's own exact trigger. A silently, permanently broken session with no recovery except a fresh login is a categorically worse failure mode than a several-second-slower notification, so this stays polling rather than chasing SSE's exact trigger further.

**Disabling a file or folder**: `_isFileDisabled(name)` is true when the name ends in `.json.disabled` or any ancestor segment is `.name.disabled`. `_makeTab()` adds `is-disabled` (dim + strikethrough) either way. `renderEditor()` separately toggles `file-disabled` (opacity only, no strikethrough/pointer-events) on `#editor-area` so a disabled file's *content* looks dimmed too, not just its tab — it stays fully editable/saveable. Only top-level folders get a Disable/Enable action.

Text lives in `data-tooltip`, not `title`, so the browser's own tooltip never engages (leaving `title` set too would show a second, native tooltip layered on the custom one in an ordinary browser tab). `_wireHoverTooltip(el, text)` sets `data-tooltip` once (when `text` is given) and reads it live on every `mouseenter` — later code can update `el.dataset.tooltip` directly (e.g. `toggleTerminal()` swapping Show/Hide) with no re-wiring needed. Shows after a 1000ms delay (`_hoverTooltipTimer`) rather than instantly on `mouseenter` — `_hideHoverTooltip()` cancels a still-pending timer too, not just an already-visible tooltip, since otherwise leaving an element (or a menu closing) right after hovering it could still pop the tooltip up later against a now-irrelevant or removed anchor. For the same reason, `mouseenter` itself cancels any existing pending timer before scheduling its own: `mouseenter` fires on an ancestor too when the pointer moves directly onto a nested descendant (e.g. a file tab inside `.tab-row-root`, whose own hover hint is "Right-click for New file / New folder") — without the cancel, the ancestor's timer would just get silently overwritten in `_hoverTooltipTimer` rather than canceled, leaving it uncancelable and free to fire later on its own regardless of what's hovered by then, which briefly showed the wrong (ancestor's) tooltip in practice. `_wireHoverTooltip()` also calls `_hideHoverTooltip()` on `click` — a click means the user already knows what the button does, and `mouseenter` can't refire without the pointer actually leaving and re-entering, so this alone is enough to stop a still-pending or already-shown tooltip from lingering while the cursor rests there afterward without moving; it shows again normally on a genuine future hover. Positioned near the actual cursor coordinates, not the hovered element's own `getBoundingClientRect()` — a wide element (a long tab, a terminal command button) would otherwise anchor the tooltip to its edge, potentially far from where the pointer actually is; below-and-right of the cursor by default, flipping to whichever side has room when there isn't (e.g. near the bottom or right edge of the viewport). The coordinates (`lastX`/`lastY`, closed over per element) are updated on every `mousemove` while hovering, not just captured once on `mouseenter` — otherwise the tooltip showed up wherever the pointer *entered*, not wherever it actually is once the delay elapses and it appears, which felt disconnected from the cursor on anything larger than a small icon. The delay itself is re-armed by both `mouseenter` and `mousemove` (a single `rearm` handler wired to each) rather than started once on entry: the delay means "show 1s after the pointer stops moving entirely," not "show 1s after it first arrived," so continuous movement — even within the same element — should never let it appear, and moving again once it's already shown should dismiss it rather than let it keep following the cursor without a fresh full pause. `rearm` calls `_hideHoverTooltip()` (canceling any existing timer, hiding an already-visible tooltip) before scheduling a new one, which also covers the nested-element case above: an ancestor's own timer gets explicitly canceled by a descendant's `mouseenter` rather than silently orphaned. `_hoverTooltipOwner` guards the same nesting problem for `mousemove` specifically, which (unlike `mouseenter`/`mouseleave`) bubbles: every movement over a nested descendant (e.g. a tab inside `.tab-row-root`) also fires `rearm` on the ancestor via bubbling, and since bubbling reaches the ancestor *after* the descendant's own listener, the ancestor's reschedule would otherwise win on every single pixel of movement — so whatever ends up pending right before the pointer actually stops was always the ancestor's tooltip, not the element genuinely being hovered. `rearm` skips rescheduling when `_hoverTooltipOwner` is a more specific element already contained by `el` (i.e. `el` is an ancestor of the current owner) — only a more specific or equal element is allowed to take over. `_initHoverTooltips(root)` wires every already-`data-tooltip`-tagged element under `root` in one pass — run once at init against `document.body` for every element whose tooltip text is static markup; elements created dynamically (tabs, the flat-mode drag handle and row actions, `_renderButtonRow`'s command buttons, the Autocomplete/Backups header buttons, the install-mode-disabled row, `makeCustomSelect` options) call `_wireHoverTooltip` directly instead, since a one-time sweep can't reach them. `_closeContextMenu()` calls `_hideHoverTooltip()` explicitly, since removing a hovered element from the DOM doesn't reliably fire its own `mouseleave`. This was tried once as a menu-items-only fix (native title's failure to retrigger switching between adjacent elements) before the app-mode root cause was confirmed and the fix broadened to every button, then further broadened again to every remaining native-title hint in the app once confirmed the underlying app-mode problem wasn't button-specific — the earlier, narrower attempts were reverted along the way in favor of each broader one |
| Tree sidebar | `renderTree`/`toggleTree` — hidden by default, persisted via `localStorage['ezconf-tree-visible']`. `#sidebar` lives inside `#main` (a sibling of `#editor-area`, not `.layout`) and is `position: absolute` there, floating over the editor's content instead of occupying its own column at the screen edge — `.main` is its positioning context (`position: relative`) |
| Markdown panels | `initMarkdownMenu`/`showMarkdownMenu`/`openMarkdownFile`/`closeMarkdownPanel` — `initMarkdownMenu()` fetches every `*.md` file under `NIXOS_TARGET` (recursive, see `/api/v1/markdown-files` above) once at load, only to decide whether to reveal the "Documents" button/wrapper (`hidden` in markup unless the list is non-empty) and to reopen whichever docs were open on the last visit. `showMarkdownMenu()` (the click handler) re-fetches the list fresh on every open instead of reusing that initial one, so a file added/removed on disk after page load shows up without a reload; it then opens a `showBackupsMenu()`-style dropdown (one entry per file, prefixed `✓` if already open, or a disabled "No .md files found." row if the fresh fetch comes back empty) — picking an already-open file's entry closes it, so multiple files can be open side by side instead of one replacing another. `_openMarkdownPanels` (name → panel element, a `Map`) is both the open-file registry and the "is this open" check, and its iteration order doubles as stacking order (last = frontmost) — deleting and re-setting an existing key moves it to the end, which is exactly what `_bringMarkdownPanelToFront(name)` uses to "raise" a panel. `openMarkdownFile()` creates a `.markdown-panel` element (fetching that file's content fresh every time, not cached, so reopening after an on-disk edit shows the current content), appends it to `#markdown-panels`, and wires a `mousedown` listener (guarded against the close button) that calls `_bringMarkdownPanelToFront`, same as clicking a background window; `closeMarkdownPanel(name)` removes just that one. Panels cascade rather than sitting side by side: `.markdown-panel` is `position: absolute`, all anchored to the same base position (`right: 0`), and `_layoutMarkdownPanels()` (called after every open/close/raise) sets a `--from-front` custom property per panel, offsetting each one leftward via `.markdown-panel`'s own `transform: translateX(calc(var(--from-front) * -40px))` in style.css proportional to its distance from the front — so every open file keeps a clickable sliver peeking out no matter how many are open, instead of later ones fully covering earlier ones. `#markdown-panels` and `#sidebar` (the tree) both live inside `#main` as `position: absolute` overlays (`.main` is their positioning context, `position: relative`) floating over `#editor-area` instead of occupying their own column and shrinking it. The open set + stacking order persists via `localStorage['ezconf-markdown-open']` (JSON array, in current stacking order), same idea as the tree sidebar's own visibility flag. `parseMarkdown()` is a small dependency-free Markdown→HTML parser ported near-verbatim from `github.com/kalken/ezblog`'s `app.js` — raw HTML in the source passes through unescaped outside code spans/blocks, same as that source, acceptable since these files are read straight from `NIXOS_TARGET`'s root, which an authenticated ezconf user already has full local access to |
| Drag-and-drop | `makeDraggable`, `reorderKey`, `moveValueToFile` — no dedicated handle, `mousedown` anywhere on a row starts a drag unless the target is an interactive element. Dropping on a different file's tab moves the value there (merging via `_mergeOrReplace`) |
| Copy/cut/paste | `copyPath`, `cutPath`, `pastePath` — deep-merges into an existing destination value (`_mergeOrReplace`/`_nixDeepMerge`) when both sides are objects, otherwise replaces |
| Context menu | `showContextMenu`, `_commonMenuItems`, `_addOptionMenuItems` — right-click everywhere instead of visible icon buttons (flat mode and package chips are the two exceptions, left as visible buttons). An item's optional `title` shows as a hover tooltip via `_wireHoverTooltip(btn, item.title, 'right')` (see "Tooltips" above) — `_buildMenuLevel()` itself doesn't otherwise show any per-item detail, so a menu built without one is silent on hover; `_buildButtonMenuItems()` sets it to each button's `command` (a leaf) or a comma-joined summary of what's inside (a submenu-group item), matching what `_renderButtonRow()` shows on a standalone bar button. An item with `items` opens a nested flyout instead of running an action, positioned to the right of the triggering item via `_positionSubmenu()` (flips left on overflow); the item itself gets a `has-submenu` class for a small `▶` indicator so it's visually distinguishable from a plain leaf action. Opens on click (same as every other menu in this app, and the only way it fires on touch) or immediately on `mouseenter` — like a native OS menu's submenus, e.g. Windows' Start menu. `_ctxMenuStack` (not a single element) tracks every open level so outside-click/Escape close the whole stack; opening a new submenu at a given depth trims anything already open past that depth first, so only one branch is ever open at a time. `showContextMenu`'s default positioning is click-point-based (`_positionMenuEl`); passing `{ anchorRect }` instead opens a dropup above and left-aligned with that rect, the same 4px gap `showExportMenu()`/`showBackupsMenu()` use below their own buttons just mirrored upward (`_positionMenuAboveAnchor`, falling back to below with that same gap if there's no room above) — used by `showButtonMenu()` since the terminal button bar sits at the bottom of the page, where a normal downward dropdown would open detached from the button or off-screen. Nested submenus are used by button `menu` grouping (below) — the only current source of nested items — but both capabilities are general `showContextMenu` features, not button-specific. `renderButtons()` calls `_closeContextMenu()` unconditionally on every render (any edit triggers one via `renderAll()`) — it rebuilds the whole button bar from a fresh `getAllButtons()`, which can shift or invalidate the indices a currently-open button dropdown was built from, so a stale menu left open could otherwise go on to run the wrong command. `opts.triggerEl` (tracked as `_openMenuTriggerEl`, cleared inside `_closeContextMenu()` so it can't go stale regardless of how the menu closed) makes a second click on the same button that opened a menu close it instead of closing-then-immediately-reopening the same thing, which is what would otherwise happen since `showContextMenu` always tears down whatever's open first — every button-triggered dropdown (`showButtonMenu`, `showExportMenu`, `showImportMenu`, `showBackupsMenu`) passes its own button as `triggerEl`; right-click menus leave it unset, since reopening fresh on a repeat right-click is the expected behavior there |
| Import | `doImport`, `_nixDeepMerge` — deep-merges pasted/loaded Nix or JSON into the "Import into" file, creating it on the fly if new |
| Zip export/import | `createZip`/`readZip` — hand-rolled zip codec using the browser's native `CompressionStream`/`DecompressionStream('deflate-raw')`, no library. `exportFile`/`exportFolder`/`exportAll` read from in-memory `fileConfigs` (unsaved edits included). `exportSystem()`/`importSystem()` are unrelated — server-side, via `GET /api/v1/system-export` and `POST /api/v1/system-import`; `importSystem()`/`restoreSystemBackup()` (see "Backups" below) are the only two `confirm()`s left in the app, since both are genuinely irreversible direct-disk writes. `initSystemImportButton()` reloads the page on success if nothing's dirty (same rule as restart detection), since the import can change `CONFIG_DIR`'s contents with no other way for the in-memory state to notice; `restoreSystemBackup()` follows the same reload-if-clean rule |
| Backups | `showBackupsMenu()` — the "🕐 Restore" button's dropdown, split into "File" and "System" submenus (same shape as "⬆ Export"/"⬇ Import"). "File" is the pre-existing per-file behavior: `GET /api/v1/backups?file=` lists past saves of the active tab (`backup_config()`/`BACKUP_DIR` — made automatically on every save), `loadBackup()` loads one into the editor as an unsaved edit, no confirmation, since nothing touches disk until Save. "System" covers the whole-`NIXOS_TARGET` tree (`backup_system()`/`SYSTEM_BACKUP_DIR`) — there's no manual "back up now" action; a system backup is only ever created automatically, right before `system-import`/`system-backup/restore` overwrites something, so `GET /api/v1/system-backups`'s list is really a history of "state right before the last few destructive writes." Each listed backup is itself a leaf that calls `restoreSystemBackup()` (`POST /api/v1/system-backup/restore`) directly, with its own confirmation — no separate download action, since downloading a system backup for its own sake isn't something this app supports. A restore is stronger than an import: `_restore_system_zip()` (server.py) additionally deletes any in-scope file (per `_iter_system_export_files()`'s own selection) the backup doesn't mention, so the tree actually reverts to the backup's exact state rather than merging into whatever was already there — `system-import`'s own write path, `_apply_system_zip()`, intentionally stays a non-destructive merge, since an arbitrary uploaded zip isn't necessarily built with a backup's exact file selection. Both `system-import` and `system-backup/restore` call `backup_system()` first, unconditionally (a no-op when system backups are disabled) — every write to `NIXOS_TARGET` from either path is destructive, so there's always a way back to what was there a moment before, without the user needing to have thought to back up first |

**`_expr` objects** (`{ _expr: "..." }`) are scalar fields toggled to raw Nix, or elements of package arrays. `isExprPkg(v)` distinguishes the two. `renderPkgArray` handles arrays at paths ending in `systemPackages`/`packages`/`extraPackages`/`extraPlugins`/`users.users.<name>.packages`.

**`renderEnumArray`** handles arrays whose option type parses as an enum (`parseEnumOptions`, e.g. `emulatedSystems`) — same chip-list UI as `renderPkgArray` but picking from the option's own enum values and appending plain strings.

**`_disabled` objects** are rendered by `renderDisabled`, which delegates to the normal renderer for the inner value and adds `is-disabled`. `isDisabled(v)` also guards `renderObj`/`renderTreeLevel` (disabled nodes render as tree leaves).

**`_commonMenuItems(path, { skipDisable })`** omits Disable/Rename for array-indexed paths (checked via `Array.isArray` on the parent, not by guessing from the segment's shape) — disabling/renaming a single array item isn't supported end-to-end (`json2nix.nix`'s `resolveExprs` only filters `_disabled` out of attrsets, and array items have no stable name).

**Autocomplete data**: `/autocomplete/{options,packages,kernels}.json`, served from `AUTOCOMPLETE_DIR` when set, else `autocomplete/` under WEBROOT.

**Rendering** is always a full re-render via `renderAll()` — no virtual DOM, no diffing.

## Terminal panel

xterm.js 6.0.0 + `@xterm/addon-fit` 0.11.0 + `@xterm/addon-webgl` 0.19.0, bundled locally in `webroot/addons/` (no CDN). WebGL loads opportunistically, falling back to Canvas 2D. UMD globals: `Terminal`, `FitAddon.FitAddon`, `WebglAddon.WebglAddon`.

Key constraints:
- `ResizeObserver` on `#term-output` is debounced 200ms so `fit()` only fires once the panel's CSS transition (180ms) settles.
- `fit()` is the only thing that triggers a PTY resize. `connectTerminalWs()`'s `onopen` calls it explicitly and sends `_term.cols`/`_term.rows` unconditionally (not `proposeDimensions()`, which is a pure calculation that can be stale right after a fast reconnect, and not gated on `onResize` firing, since a brand new server-side session — e.g. after `ezconf-terminal-session.service` restarts independently — has never been told any size at all).
- Never use a continuous `requestAnimationFrame` loop for rendering — on Linux without GPU acceleration it burns CPU proportional to canvas size.
- `setTheme()` calls `_termFit.fit()` explicitly once the new theme CSS loads, in addition to rebuilding `_term.options.theme` (colors) — a theme swap changes `--term-padding` too, which affects `#term-output`'s content box without changing its own outer size, so the `ResizeObserver` that normally drives `fit()` never fires for it; without the explicit call the terminal kept rendering at its pre-swap size/position until something else forced a fresh `fit()` (e.g. a full page reload).
- `--term-padding` (currently 4px) lives on `#term-output`, not on `.terminal.xterm` (xterm's own root element, a child `Terminal.open()` creates inside it, explicitly zeroed out) — despite `FitAddon.proposeDimensions()` reading `padding-*` from `.terminal.xterm` specifically when computing rows/cols, not from its parent, so `#term-output`'s padding is invisible to that calculation and the grid is sized for the full unpadded area, clipped by a few pixels at the bottom/right under `#term-output`'s own `overflow: hidden`. That mismatch is real, but negligible at this small a value — tried moving the padding to `.terminal.xterm` instead (which *does* get read by the fit calculation) and that produced visibly uneven padding in practice instead, for reasons not fully understood (likely xterm's internal canvas layers not respecting their own container's padding symmetrically) — reverted back to this approach as the better trade-off. Don't move it back to `.terminal.xterm` without re-verifying that actually looks right.

**CSS file roles**: `style.css` = layout, `theme-{nixos,dark,light}.css` = per-theme variables, `addons/xterm.css` = vendor file (unmodified).

**Panel open/size persists across reloads** (`ezconf-terminal-open`/`ezconf-terminal-size` in `localStorage`, same convention as `ezconf-tree-visible`) — `toggleTerminal()`/`setTerminalSize()` write it via `_persistTerminalOpen()`/`_persistTerminalSize()`, restored once at init via `setTerminalSize()` (not `toggleTerminal()`, since that relies on `panel._openHeight`, a plain JS property that never survives a reload — `setTerminalSize()` recomputes the actual height fresh from the size name instead, which "full" needs regardless, being a live `calc()` against other elements' current heights rather than a value that could itself be persisted). This is purely per-browser UI state, independent of the terminal *session* itself (`_SESSION` in `bin/terminal.py`, shared by every browser — see "Session persistence" above) — restoring the panel to open doesn't imply anything about whether persistence is enabled or a shell is still running underneath.

The command-button bar sits below the terminal output, not above it — `.terminal-body` comes first in markup, and `.terminal-header`/`#terminal-header-install` are wrapped in `.terminal-header-group`, `position: absolute; bottom: 0` on `.terminal-panel` (itself `position: relative`) rather than plain flex children. That's deliberate, not just styling: as an ordinary flex child sharing the column with `.terminal-body`'s `flex: 1`, the header only ever sat at the bottom because the body above it was pushing it down — the instant `.terminal-panel.collapsed .terminal-body { display: none; }` removed that body from the flex calculation, the header snapped up to fill the vacated space instead of collapsing smoothly. Taking it out of flow entirely and pinning it to the panel's own bottom edge keeps it visually anchored there through the whole collapse/expand transition regardless of what the body is doing. `.terminal-body` carries a matching `padding-bottom` (33px, or 66px via `.terminal-panel.install-mode`) so its own content doesn't render underneath the now-overlaid header group. `.terminal-header`'s divider border is `border-top` (not `border-bottom`), matching the bar now sitting below rather than above.

**Theming rule**: any new customizable CSS value (colors, radii, sizes, spacing) must be a variable in all three theme files. Hard-coded values in `style.css` are only for structural properties that should never vary.

**Install mode** (`EZCONF_MODE`, set by `mode` in `ezconf.toml` / `services.ezconf.mode` in the NixOS module — deploy-time only, no CLI flag, no in-GUI toggle): a button with `mode = "install"` renders into a second row (`#terminal-cmd-btns-install`) instead of the ordinary one; that row is hidden unless `EZCONF_MODE === 'install'` (`INSTALL_MODE`). `renderButtons()` splits `getAllButtons()`'s result by `btn.mode` into two entry lists, each still indexed into the full list so `runButton()`/`showButtonMenu()` need no changes. The whole ordinary row (not each button) is disabled at once via a CSS class + `title` tooltip, both set once at init when `INSTALL_MODE` is true — the container-level `pointer-events: none` covers every button regardless of its own state, so `_updateDirty()`'s `save_first` toggle needs no install-mode awareness. The init code also adds `install-mode` to `#terminal-panel`, which a CSS rule bumps to `height: 66px` (collapsed) to fit both rows.

## Nix flake

`flake.nix` exposes four packages (`modules/ezconf-packages.nix`):
- `ezconf` — web server + assets; `--webroot` defaults to the Nix store share dir
- `ezconf-terminal` — `bin/terminal.py` as a standalone binary, separate derivation so asset changes don't restart the terminal service
- `ezconf-mkoptions` — `bin/generate-nixos-data.py` with nix + python-pam + cryptography in PATH
- `ezconf-mkcerts` — `mkcert`-based dev-cert helper

The `ezconf` derivation installs `webroot/` and `bin/server.py`. Autocomplete data is not installed — it's user-generated, belongs in a writable directory.

**Version tracking**: `ezconf-packages.nix` takes a `version` argument (default `"dev"`) written verbatim into `$out/share/ezconf/VERSION` at build time — right inside `WEBROOT`, alongside `index.html`/`style.css`, so it's already served as a plain static file with no server.py involvement at all. `initVersion()` fetches `VERSION` once at page load and fills in `#status-version` in the statusbar (`"version: " + content`, or `"version: dev"` on a 404 — the normal case for a plain `python3 server.py` run straight from a git checkout, no Nix build). Both `flake.nix`'s own `packages.ezconf` and `modules/ezconf.nix` (the NixOS module — `self.shortRev or "dev"`, `self` being ezconf's *own* flake self-reference regardless of which flake consumes it as an input) pass `self.shortRev`, so a deployed system's VERSION file reflects exactly which commit the consuming flake's `flake.lock` has ezconf pinned to. `self.shortRev` (like `self.rev`) is only set for a clean, committed git tree — a dirty checkout falls back to `"dev"` via `or`, not an eval error.

## NixOS module (`modules/ezconf.nix`)

Two systemd services under `services.ezconf.enable`:
- `ezconf.service` — restarts normally on rebuild (what restart-detection watches for)
- `ezconf-terminal.service` — only when `terminal = true`; `restartIfChanged = false` since it forks the shell directly as its own child, so restarting the unit would kill whatever's running inside it

Key options: `user`/`group` (default `root`), `https`/`generateCert`/`installCerts`/`cert`/`key`, `auth.{method,username,password,passwordFile,allowedUsers}`, `theme`, `mode` (see "Install mode"), `terminal`, `terminalPersist` (off by default — see "Session persistence" above), `nixosTarget`, `systemExportExcludeDotfiles`/`systemExportExclude`, `backupDir`/`backupCount`, `systemBackupDir`/`systemBackupCount` (a whole-`nixosTarget` zip snapshot made automatically right before a system import/restore overwrites anything, never on a manual trigger, unlike the automatic-on-save per-file backups), `listen`/`interface`/`openFirewall`, `ports.{web,terminal}`, `configDir` (default `/etc/nixos/ezconf`, starts with **zero** tabs — see below), `defaultFile`, `trustedHosts` (`[ "*" ]` disables the CSRF Host check entirely), `buttons` (`{label, command, save_first, clear_first, menu, mode, static}` — every `*.json`-declared button shows regardless of which tab is active, but a button declared directly here in Nix only shows if `static = true` (see `STATIC_BUTTONS` above); `menu` groups same-named buttons into one dropdown, and nests further via "/" (e.g. `"Disk/Advanced"`) into a submenu inside that dropdown — see `_buildButtonMenuItems()`/the Context menu row above; `mode = "install"` moves a button into the install-only row).

**Why `configDir` starts empty**: an earlier version seeded `defaultFile` with `{}` on every activation if missing, which fought renaming/moving it directly — the next rebuild would silently recreate it, colliding with a later rename back to that name. `json2nix.nix`'s `lib.mkMerge` over zero files evaluates to `{}` fine, so an empty `configDir` is a valid, if inert, state — `renderEditor()`'s empty-state message offers New file/folder directly.
