## What this is

A zero-dependency, single-page NixOS configuration editor. No build step, no framework, no package manager. `bin/server.py` serves the app and edits the `*.json` config files under a directory given via `--file`, discovered recursively (except `custom-options.json`, a schema-extension sidecar, and dotdirs like the default `.ezconf-backups`) — each file an independently editable/saveable/backed-up "file," chosen via a dropdown in the header, merged together only at Nix-eval time via `lib.mkMerge` in `json2nix.nix`. Files can be nested in subfolders (e.g. `services/nginx.json`) purely for organization. `--file` can also name a specific `*.json` file — its directory becomes the working set, and it's preselected initially.

## Running

```sh
python3 bin/server.py                          # reads ezconf.toml in CWD (or --config FILE)
python3 bin/server.py --webroot DIR --file FILE # CLI args override the config file
python3 bin/server.py --generate-cert [DIR]     # self-signed cert for dev use
python3 bin/server.py --generate-ca [DIR]       # local CA + server cert (used by the NixOS service)
nix run .#ezconf -- --file /path/to/configuration.json
```

Python deps (all optional, all in the flake devShell): `python-pam` (PAM auth), `cryptography` (`--generate-cert`/`--generate-ca`), `tomli` (TOML config on Python < 3.11).

Auth: `--auth auto` (default — PAM if available, else custom), `--auth custom` (username/password from config), `--auth pam`. `allowed_users` in config restricts PAM logins and renders a dropdown instead of a free-text username field. Authentication is always required.

Terminal: a separate process, `bin/terminal.py`. Pass `--terminal-port PORT` to `server.py` to enable the panel; run `terminal.py --config ezconf.toml` on the same port.

## Generating data files

`bin/generate-nixos-data.py` generates the JSON files the editor needs; exposed via the flake as `ezconf-mkoptions`:

```sh
ezconf-mkoptions                          # all files → webroot/autocomplete/
TARGET=/path/to/flake ezconf-mkoptions all myhostname
ezconf-mkoptions options   # only options.json
ezconf-mkoptions packages  # only packages.json
ezconf-mkoptions kernels   # only kernels.json
ezconf-mkoptions -v        # verbose nix errors (otherwise a failed nix eval is silent)
```

Shells out to `nix eval --json`; `TARGET` env var sets the flake path (default `/etc/nixos`). Output defaults to `autocomplete/` under CWD (`-o DIR` to override) — it belongs inside WEBROOT so the server can serve it, and is gitignored (user-specific generated data).

When `hostname` is omitted (as both `ezconf.service`'s `preStart` and `/api/v1/autocomplete/update` do — neither passes one), it's not just `hosts[0]`: `socket.gethostname()` is checked against the flake's `nixosConfigurations` first, since `networking.hostName` is what actually becomes the running machine's hostname — this picks the right host automatically on a multi-host flake instead of an arbitrary one. Only falls back to `hosts[0]` if the machine's own hostname isn't one of the flake's hosts (e.g. generating for a different target than the one you're running on).

Every `nix eval` call goes through one `nix_eval()` helper, which adds `--no-allow-import-from-derivation` (this only ever needs declarative metadata, never a build — a third-party module like disko defining a type/default that reads real hardware should fail fast, not hang) and a 600s timeout (`NIX_EVAL_TIMEOUT`), printed as a one-line warning unconditionally on timeout (unlike a normal failure, which needs `-v`). Without the timeout, a hung eval could block `ezconf.service`'s own `preStart` past systemd's startup timeout and fail the whole service.

`nix_eval()` returns `None` on any failure (a distinct value from a legitimately empty result). Every call site that feeds it into `generate_packages()`/`generate_options()`/`generate_kernels()` checks for `None` explicitly and calls `warn()` before falling back to `[]` — a bare `nix_eval(...) or []` was tried first and rejected, since it made a *total* eval failure (e.g. a host's `configuration.nix` importing a `hardware-configuration.nix` that doesn't exist at `TARGET`) silently produce an empty, "successful" output file with no diagnostic at all, indistinguishable from a file that legitimately has zero entries.

`generate_options()` filters out `internal = true` options before touching them (the NixOS convention for "not meant to be set directly," e.g. disko's underscore-prefixed options) and wraps every field (`description`/`type`/`default`/`example`/`required`) in `safeGet()`, which runs `builtins.tryEval (builtins.deepSeq v v)` rather than plain `tryEval (f opt)` — `nix eval --json` has to force every field to serialize the result, and plain `tryEval` only protects against a throw while forcing to shallow WHNF; a value that's itself a nested attrset can pass that check and only throw later when something forces a field inside it. `deepSeq` forces the whole structure up front, inside the guard, so nested throws (e.g. a disko default that reaches into a nonexistent realized `config`) are actually caught instead of aborting the entire options list.

## Server architecture (`bin/server.py`)

Single `ThreadingHTTPServer` bound to `BIND_ADDR:WEB_PORT` (default `127.0.0.1:9090`). `StaticHandler` (subclass of `SimpleHTTPRequestHandler`) serves static assets and handles the API. All endpoints below require auth except `/download-ca`.

**API endpoints**:
- `GET /download-ca` — serves `CA_FILE` as a downloadable PEM, when set
- `GET /api/v1/ping` — one-off check the frontend calls only when the SSE stream below errors out, to detect a dead session (401) that auto-reconnect can't fix on its own
- `GET /api/v1/ping-stream` — `{boot_id, webroot_hash, theme, terminal_enabled, mkoptions_enabled, backup_enabled, nixos_target, buttons}` pushed over a held-open SSE connection; the restart signal is the connection dying when the process exits, not the payload changing — see "Restart detection" below
- `GET /api/v1/files` — `{files, folders, default}`; `folders` lists every subdirectory including empty ones (so an empty folder still shows as a tab group after reload)
- `GET /api/v1/file?file=NAME` — raw JSON content of the resolved config file (falls back to `DEFAULT_FILE`)
- `POST /api/v1/file/save?file=NAME` — writes the file, backing up the previous contents first; creates it if new
- `POST /api/v1/autocomplete/update` — reruns `MKOPTIONS_CMD -v`; only available when `--mkoptions` is set. Exit 0 alone isn't treated as success: `generate-nixos-data.py` can exit 0 while a total eval failure left `options.json`/`packages.json`/`kernels.json` as an empty `[]` (see "Generating data files"), so `_is_empty_json_array()` checks the actual output files in `out_dir` first — any of them coming back empty is treated as a failure even on exit 0. On any failure (empty files, or a genuinely nonzero exit), the full captured stdout+stderr (ANSI-stripped via `_strip_ansi()`) comes back as `error`, so `-v`'s detailed trace is what the frontend shows in a modal (`showMkoptionsOutputModal()`) — a bare success just returns `{"ok":true}` with no popup, since checking real files rather than parsing log text is what lets a clean run stay quiet without needing to filter `generate-nixos-data.py`'s routine `info()` progress lines out of anything
- `GET /api/v1/system-export` — zips the entire `NIXOS_TARGET` tree (not just `CONFIG_DIR`) via `_iter_system_export_files()`; always skips symlinks; skips dotfiles/dotdirs and `hardware-configuration.nix` by default (`SYSTEM_EXPORT_EXCLUDE_DOTFILES`/`SYSTEM_EXPORT_EXCLUDE`, both configurable, since hardware-configuration.nix is machine-specific and shouldn't be bundled into something meant as a template)
- `POST /api/v1/system-import` — writes a zip's files directly into `NIXOS_TARGET`, immediately, no Save step, no undo; validates every entry (rejects path traversal, dotfiles) before writing any of them; overwrites same-named files, never deletes anything the zip doesn't mention
- `GET /api/v1/backups?file=NAME` — lists backups in `BACKUP_DIR` for that file, newest first
- `GET /api/v1/backup/content?name=NAME` — a backup's raw content; read-only, the frontend loads it as an unsaved edit
- `POST /api/v1/file/delete` — deletes a config file; zero files afterward is a valid state
- `POST /api/v1/file/rename` — renames/moves a file (covers moving between folders too); also how a file is disabled/enabled, via renaming to/from `NAME.json.disabled` (`json2nix.nix`'s glob requires an exact `.json` suffix, so no changes needed there)
- `POST /api/v1/folder/create` / `folder/delete` — create (`os.makedirs`) / delete (`shutil.rmtree`, recursive) a subfolder
- `POST /api/v1/folder/disable` / `folder/enable` — renames a folder to/from `.NAME.disabled` (dot-prefixed, so `json2nix.nix` skips it like any dotdir); everything nested moves for free with one rename

**File routing**: `resolve_config_path()` accepts a relative path or its `.disabled` form and keeps writes inside `CONFIG_DIR` (a correctness guard, not a security boundary — an authenticated user already has terminal access). `list_config_files()`/`list_config_folders()` walk `CONFIG_DIR` skipping dotdirs, except a disabled folder (`.NAME.disabled`) is still walked so its files keep listing as disabled tabs. Backup filenames flatten the relative path (`services/nginx.json` → `services--nginx`) so `BACKUP_DIR` stays flat even with nested tabs.

**Disabling a file or folder** is a pure filesystem rename, not a content change — round-trips losslessly, and the disabled file/folder stays fully viewable/editable/saveable, just excluded from the Nix merge. A file: append `.disabled`. A folder: dot-prefix and suffix its own directory name (`services` → `.services.disabled`) — only top-level folders get this in the UI.

**Key globals**:
- `WEBROOT`, `CONFIG_DIR`, `DEFAULT_FILE` — static assets dir, config files dir, preferred initial tab
- `AUTOCOMPLETE_DIR` — override for `/autocomplete/*`; `MKOPTIONS_CMD` — enables the autocomplete/update endpoint
- `NIXOS_TARGET` — flake path for mkoptions and for `system-export`
- `SYSTEM_EXPORT_EXCLUDE_DOTFILES` / `SYSTEM_EXPORT_EXCLUDE` — export exclusion config (defaults: `True` / `{'hardware-configuration.nix'}`)
- `THEME`, `EZCONF_MODE` (`None` or `'install'` — deploy-time only, see "Install mode" below), `TERMINAL_PORT`
- `BIND_ADDR`, `TRUSTED_HOSTS` — CSRF Host-header allowlist for `_valid_host`; `"*"` disables the check entirely (for cases like an installer ISO where the reachable address can't be known ahead of time)
- `CA_FILE`, `BACKUP_DIR`, `BACKUP_COUNT`
- `STATIC_BUTTONS` — deploy-time terminal buttons from `[[buttons]]` in TOML; deduped against per-file `services.ezconf.buttons` by `label`+`command` identity in `getAllButtons()` (`_buttonIdentity()`), since the latter becomes the same NixOS option (and thus the same `STATIC_BUTTONS`) once saved and rebuilt — a live edit sharing that identity supersedes and drops the stale static entry, so e.g. adding `menu` to an already-deployed button doesn't show both the old standalone button and the new grouped one until the next rebuild
- `_SESSION_KEY` — expected `ezconf_session` cookie value
- `BOOT_ID` — fresh random hex every process start, never persisted (unlike `_SESSION_KEY`) — lets the frontend detect a different process is now serving the page
- `WEBROOT_HASH` — SHA-256 of `index.html`/`style.css`/theme CSS files, computed once at startup; only changes across a restart when the frontend itself actually changed (a real package upgrade), unlike `BOOT_ID` which changes on every restart

**Auth flow**: `/login` sets `Set-Cookie: ezconf_session=<SESSION_KEY>; HttpOnly; SameSite=Strict`. `check_auth()` compares that cookie to `_SESSION_KEY`.

**PAM auth**: `check_pam()` creates a fresh `pam.pam()` instance on every call — never use a global instance, it segfaults on Linux after the first `authenticate()` call.

## Terminal service (`bin/terminal.py`)

Separate process, own port (default 9091), WebSocket-upgrades a PTY session. `_terminal_ws()` forks the configured shell; resize messages call `fcntl.ioctl(TIOCSWINSZ)`; `pty_to_ws` polls with `select` (0.5s timeout).

Reads the same `ezconf.toml`. Authenticated via the `ezconf_session` cookie on the upgrade request. Runs as `ezconf-terminal.service`, separate from `ezconf.service`, with `restartIfChanged = false` so terminal sessions survive `nixos-rebuild switch`.

**Persistent sessions via dtach** (`services.ezconf.terminalPersist`, default `false`): normally `launch_shell()` forks a fresh shell directly into the connection's own PTY, so the shell dies with the connection (or with `ezconf-terminal.service` itself). When `dtach_socket` is set in TOML, it instead execs `dtach -a SOCKET -r winch -E -z` (attach to an existing session) rather than the shell directly — the shell lives in a separate, persistent process (`ezconf-terminal-session.service`, started via `terminal.py --start-session`, which `os.execv`s into `dtach -N SOCKET -r winch -E -z SHELL -l`), so it survives `ezconf-terminal.service` restarting or a reconnect. `-E`/`-z` disable dtach's own detach/suspend-key interception (nothing in-band should detach; the WebSocket closing is what that means here) — verified empirically that resize (`set_winsize()`'s existing `TIOCSWINSZ` ioctl) propagates through `-r winch` live, not just at attach time, so no other changes were needed there. `DTACH_BIN` is resolved via `shutil.which()`; `DTACH_SOCKET` is only honored if `dtach` is actually found, so a deployment without it installed falls back to today's non-persistent behavior rather than failing.

This needs its own systemd unit, not just a config flag — `KillMode=control-group` (systemd's default) kills every process in a unit's cgroup on stop, including descendants dtach forked and reparented to PID 1, since orphaning doesn't move a process to a different cgroup. Putting the session in `ezconf-terminal-session.service` (its own unit, `restartIfChanged = false`, `Restart = on-failure` only) is what actually keeps it outside `ezconf-terminal.service`'s cgroup. Also empirically confirmed: the cleanup path's `proc.terminate()` doesn't reliably kill a dtach attach client — without a `proc.kill()` fallback after a short timeout, the old client leaked on every disconnect instead of exiting; this fallback applies regardless of dtach, not just in persist mode.

`ezconf-terminal.service`'s own `restartIfChanged` is `cfg.terminalPersist` — without persistence, restarting it kills whatever's running inside, so a rebuild must never do that automatically (`false`). With it, the shell lives in the separate session unit, so restarting the bridge only drops the viewing WebSocket connection for a moment (reconnecting re-attaches, nothing lost) — including if a `nixos-rebuild switch` is what's running *inside* the terminal panel when the bridge restarts: that process lives in `ezconf-terminal-session.service`'s cgroup, not the bridge's, so it keeps running untouched regardless of what happens to the bridge (`true`).

**Changing `terminalPersist` itself is the one rebuild that isn't safe from inside the panel**, in either direction. False→true: `ezconf-terminal.service`'s definition changes to the new (`restartIfChanged = true`) form, so the switch restarts it — but the *currently running* `nixos-rebuild switch` shell was forked under the old direct-shell model, as a child of that exact service, since that's what was active when the connection started; restarting it kills that command mid-flight. True→false: `ezconf-terminal-session.service` is gated by `lib.mkIf (cfg.terminal && cfg.terminalPersist)`, so it doesn't exist at all in the target config — a unit being removed between generations gets stopped outright, which isn't governed by `restartIfChanged` at all (that only applies to units that still exist but changed) — and the running switch command lives inside that exact session this time. Either direction, the switch tears down whichever architecture is currently hosting the connection running it, since that connection predates the config change and can't retroactively move. Must be triggered from outside the panel (SSH, console); any rebuild that doesn't touch this setting is unaffected.

## Frontend architecture (`webroot/index.html`)

All logic is in one `<script>` block. No modules, no build step.

**Data model**: `config` (active tab's JSON, plain object), `options` (`{path, type, description, default, example}[]`), `packages` (`{name, description}[]`). Two sentinel shapes: `{ _expr: "..." }` (raw Nix expression) and `{ _disabled: true, _value: <original> }` (option disabled in the UI, filtered by `json2nix.nix`, original value preserved for re-enabling).

**Multi-file state**: every file's config lives in `fileConfigs[name]` up front, not just the active one. `config === fileConfigs[activeFile]` always — anything that reassigns `config` wholesale (import, undo/redo, reload) must sync back, which `renderAll()` does unconditionally as a safety net. `fileSaved[name]` is the last-saved-to-disk snapshot; `isAnyDirty()` compares every file against it (plus non-empty `pendingFsOps`). `saveToServer()` POSTs every dirty file. `name` keys are `CONFIG_DIR`-relative paths.

**Live dirty-tracking vs. undo granularity**: scalar field editors call `setAtPath()` on `'input'` (per keystroke), not `'change'` (blur only) — otherwise Save stayed stale until the field lost focus. `_pushHistory()` stays on `'change'` only, so undo still records one entry per edit session, not per character. Nullable-string fields split the same way: the value updates on `'input'`, but swapping the widget itself (plain text ↔ "null" placeholder) is a full `renderAll()` (would steal focus mid-typing), so that stays on `'change'`.

Tab bar: no "+"/"new" buttons anywhere — everything is right-click (blank space → New file/folder; a tab → its own menu; a folder group → New file here/Delete folder). Tabs are `<div>`s not `<button>`s (rename swaps the label for a live `<input>`, invalid inside a real button). Double-click renames inline; dragging (custom mousedown/mousemove implementation, 5px threshold) moves a tab between folders.

**Nothing touches the server until Save** — not just content, but every filesystem-affecting action (delete, rename/move, disable/enable) for both files and folders. `pendingFsOps` is an ordered queue of operation descriptors, replayed in recorded order by `saveToServer()` before any content save, stopping at the first failure. Replaying in order (rather than collapsing into a minimal net op) is what makes a chain of edits to the same file — renamed twice, moved into a folder created moments earlier — replay correctly for free. `folderExists` tracks folders confirmed-or-about-to-be-confirmed on disk, the folder equivalent of `fileSaved`-presence, used to decide whether an op needs to be queued at all (a file/folder never saved has nothing on disk to touch). Delete/rename no longer prompt for confirmation — since nothing is real until Save replays it, a prompt would warn about something that hasn't happened yet.

**Undo/redo** (`globalHistory`/`_pushHistory`/`undo`/`redo`/`_restoreSnapshot`/`_applySnapshot`) is one global stack of full-state snapshots (`files`, `folders`, every `fileConfigs` entry, `fileSaved`, `pendingFsOps`, `folderExists`), not per-file — undoing a delete has to resurrect the file *and* un-queue the disk delete, which a content-only diff can't express. Deduped against the previous snapshot by everything except `activeFile`, so switching tabs doesn't spend its own undo step. Can't undo something Save has already replayed against disk — undoing back across an applied delete resurrects the file locally, but the server has no memory of it.

**Undo/redo survives a reload**: `_schedulePersistHistory()` debounces (400ms) writing `{history, index}` to `localStorage['ezconf-history-v1']`. On load, right after fresh state loads from disk, `_tryRestoreHistoryFromStorage()` searches the persisted stack newest-first for an entry whose content matches that fresh disk state, and resumes there if found — this is what decides safety, not *why* the reload happened (plain reload, hard reload, restart-triggered reload are all just "a reload"). No match (something changed on disk outside this tab's awareness) discards the whole stack rather than resuming into a lineage that no longer describes reality.

**Restart detection** (`BOOT_ID`, `initRestartWatcher()`, `_restartDetected`): `initRestartWatcher()` holds `GET /api/v1/ping-stream` open via `EventSource` rather than polling — the restart signal is the connection dying (the old process exiting), and the browser's own auto-reconnect gets the tab talking to the new process, whose first event carries a fresh `boot_id`. A changed `boot_id` alone isn't "reload now": every other field in the payload is compared against what this page actually has. `STATIC_BUTTONS` differing is patched in place with no reload (the most common actual change); `webroot_hash`/`theme`/`terminal_enabled`/`mkoptions_enabled`/`backup_enabled`/`nixos_target` differing sets `_restartDetected` (`webroot_hash` catches an actual package upgrade). Never reloads out from under unsaved edits — `_updateDirty()` fires the actual `location.reload()` once `isAnyDirty()` next reports clean. `EventSource` can't expose a response status, so the one case its reconnect can't fix (401, dead session) is checked via a one-off plain `GET /api/v1/ping` from `onerror`.

**Disabling a file or folder**: `_isFileDisabled(name)` is true when the name ends in `.json.disabled` or any ancestor segment is `.name.disabled`. `_makeTab()` adds `is-disabled` (dim + strikethrough) either way. `renderEditor()` separately toggles `file-disabled` (opacity only, no strikethrough/pointer-events) on `#editor-area` so a disabled file's *content* looks dimmed too, not just its tab — it stays fully editable/saveable. Only top-level folders get a Disable/Enable action.

| Tooltips | `buildTooltip`/`_wireTooltipAnchor` — one shared `position: fixed` tooltip element appended to `<body>`, positioned via JS from the anchor's `getBoundingClientRect()` (needed since ancestors clip `overflow`). Every hover hint in the app — header/tab-bar/theme-switcher/terminal-bar buttons, file tabs, the flat-mode drag handle and its `{ }`/`✕` row actions, `makeCustomSelect`'s option list, `status-path`, the empty-editor root row's right-click hint — uses the sibling `_showHoverTooltip`/`_hideHoverTooltip`/`_wireHoverTooltip` mechanism instead of the native `title` attribute — confirmed empirically that native tooltips render unreliably (often not at all) inside a Chromium "app mode" / installed-PWA window, which the README documents as a supported way to run this app, so relying on native tooltips at all doesn't work for every user. Text lives in `data-tooltip`, not `title`, so the browser's own tooltip never engages (leaving `title` set too would show a second, native tooltip layered on the custom one in an ordinary browser tab). `_wireHoverTooltip(el, text)` sets `data-tooltip` once (when `text` is given) and reads it live on every `mouseenter` — later code can update `el.dataset.tooltip` directly (e.g. `toggleTerminal()` swapping Show/Hide) with no re-wiring needed. Shows after a 1000ms delay (`_hoverTooltipTimer`) rather than instantly on `mouseenter` — `_hideHoverTooltip()` cancels a still-pending timer too, not just an already-visible tooltip, since otherwise leaving an element (or a menu closing) right after hovering it could still pop the tooltip up later against a now-irrelevant or removed anchor. For the same reason, `mouseenter` itself cancels any existing pending timer before scheduling its own: `mouseenter` fires on an ancestor too when the pointer moves directly onto a nested descendant (e.g. a file tab inside `.tab-row-root`, whose own hover hint is "Right-click for New file / New folder") — without the cancel, the ancestor's timer would just get silently overwritten in `_hoverTooltipTimer` rather than canceled, leaving it uncancelable and free to fire later on its own regardless of what's hovered by then, which briefly showed the wrong (ancestor's) tooltip in practice. `_wireHoverTooltip()` also calls `_hideHoverTooltip()` on `click` — a click means the user already knows what the button does, and `mouseenter` can't refire without the pointer actually leaving and re-entering, so this alone is enough to stop a still-pending or already-shown tooltip from lingering while the cursor rests there afterward without moving; it shows again normally on a genuine future hover. Positioned near the actual cursor coordinates, not the hovered element's own `getBoundingClientRect()` — a wide element (a long tab, a terminal command button) would otherwise anchor the tooltip to its edge, potentially far from where the pointer actually is; below-and-right of the cursor by default, flipping to whichever side has room when there isn't (e.g. near the bottom or right edge of the viewport). The coordinates (`lastX`/`lastY`, closed over per element) are updated on every `mousemove` while hovering, not just captured once on `mouseenter` — otherwise the tooltip showed up wherever the pointer *entered*, not wherever it actually is once the delay elapses and it appears, which felt disconnected from the cursor on anything larger than a small icon. The delay itself is re-armed by both `mouseenter` and `mousemove` (a single `rearm` handler wired to each) rather than started once on entry: the delay means "show 1s after the pointer stops moving entirely," not "show 1s after it first arrived," so continuous movement — even within the same element — should never let it appear, and moving again once it's already shown should dismiss it rather than let it keep following the cursor without a fresh full pause. `rearm` calls `_hideHoverTooltip()` (canceling any existing timer, hiding an already-visible tooltip) before scheduling a new one, which also covers the nested-element case above: an ancestor's own timer gets explicitly canceled by a descendant's `mouseenter` rather than silently orphaned. `_hoverTooltipOwner` guards the same nesting problem for `mousemove` specifically, which (unlike `mouseenter`/`mouseleave`) bubbles: every movement over a nested descendant (e.g. a tab inside `.tab-row-root`) also fires `rearm` on the ancestor via bubbling, and since bubbling reaches the ancestor *after* the descendant's own listener, the ancestor's reschedule would otherwise win on every single pixel of movement — so whatever ends up pending right before the pointer actually stops was always the ancestor's tooltip, not the element genuinely being hovered. `rearm` skips rescheduling when `_hoverTooltipOwner` is a more specific element already contained by `el` (i.e. `el` is an ancestor of the current owner) — only a more specific or equal element is allowed to take over. `_initHoverTooltips(root)` wires every already-`data-tooltip`-tagged element under `root` in one pass — run once at init against `document.body` for every element whose tooltip text is static markup; elements created dynamically (tabs, the flat-mode drag handle and row actions, `_renderButtonRow`'s command buttons, the Autocomplete/Backups header buttons, the install-mode-disabled row, `makeCustomSelect` options) call `_wireHoverTooltip` directly instead, since a one-time sweep can't reach them. `_closeContextMenu()` calls `_hideHoverTooltip()` explicitly, since removing a hovered element from the DOM doesn't reliably fire its own `mouseleave`. This was tried once as a menu-items-only fix (native title's failure to retrigger switching between adjacent elements) before the app-mode root cause was confirmed and the fix broadened to every button, then further broadened again to every remaining native-title hint in the app once confirmed the underlying app-mode problem wasn't button-specific — the earlier, narrower attempts were reverted along the way in favor of each broader one |
| Tree sidebar | `renderTree`/`toggleTree` — hidden by default, persisted via `localStorage['ezconf-tree-visible']` |
| Drag-and-drop | `makeDraggable`, `reorderKey`, `moveValueToFile` — no dedicated handle, `mousedown` anywhere on a row starts a drag unless the target is an interactive element. Dropping on a different file's tab moves the value there (merging via `_mergeOrReplace`) |
| Copy/cut/paste | `copyPath`, `cutPath`, `pastePath` — deep-merges into an existing destination value (`_mergeOrReplace`/`_nixDeepMerge`) when both sides are objects, otherwise replaces |
| Context menu | `showContextMenu`, `_commonMenuItems`, `_addOptionMenuItems` — right-click everywhere instead of visible icon buttons (flat mode and package chips are the two exceptions, left as visible buttons). An item's optional `title` shows as a hover tooltip via `_wireHoverTooltip(btn, item.title, 'right')` (see "Tooltips" above) — `_buildMenuLevel()` itself doesn't otherwise show any per-item detail, so a menu built without one is silent on hover; `_buildButtonMenuItems()` sets it to each button's `command` (a leaf) or a comma-joined summary of what's inside (a submenu-group item), matching what `_renderButtonRow()` shows on a standalone bar button. An item with `items` opens a nested flyout instead of running an action, positioned to the right of the triggering item via `_positionSubmenu()` (flips left on overflow); the item itself gets a `has-submenu` class for a small `▶` indicator so it's visually distinguishable from a plain leaf action. Opens on click (same as every other menu in this app, and the only way it fires on touch) or immediately on `mouseenter` — like a native OS menu's submenus, e.g. Windows' Start menu. `_ctxMenuStack` (not a single element) tracks every open level so outside-click/Escape close the whole stack; opening a new submenu at a given depth trims anything already open past that depth first, so only one branch is ever open at a time. `showContextMenu`'s default positioning is click-point-based (`_positionMenuEl`); passing `{ anchorRect }` instead opens a dropup above and left-aligned with that rect, the same 4px gap `showExportMenu()`/`showBackupsMenu()` use below their own buttons just mirrored upward (`_positionMenuAboveAnchor`, falling back to below with that same gap if there's no room above) — used by `showButtonMenu()` since the terminal button bar sits at the bottom of the page, where a normal downward dropdown would open detached from the button or off-screen. Nested submenus are used by button `menu` grouping (below) — the only current source of nested items — but both capabilities are general `showContextMenu` features, not button-specific. `renderButtons()` calls `_closeContextMenu()` unconditionally on every render (any edit triggers one via `renderAll()`) — it rebuilds the whole button bar from a fresh `getAllButtons()`, which can shift or invalidate the indices a currently-open button dropdown was built from, so a stale menu left open could otherwise go on to run the wrong command. `opts.triggerEl` (tracked as `_openMenuTriggerEl`, cleared inside `_closeContextMenu()` so it can't go stale regardless of how the menu closed) makes a second click on the same button that opened a menu close it instead of closing-then-immediately-reopening the same thing, which is what would otherwise happen since `showContextMenu` always tears down whatever's open first — every button-triggered dropdown (`showButtonMenu`, `showExportMenu`, `showImportMenu`, `showBackupsMenu`) passes its own button as `triggerEl`; right-click menus leave it unset, since reopening fresh on a repeat right-click is the expected behavior there |
| Import | `doImport`, `_nixDeepMerge` — deep-merges pasted/loaded Nix or JSON into the "Import into" file, creating it on the fly if new |
| Zip export/import | `createZip`/`readZip` — hand-rolled zip codec using the browser's native `CompressionStream`/`DecompressionStream('deflate-raw')`, no library. `exportFile`/`exportFolder`/`exportAll` read from in-memory `fileConfigs` (unsaved edits included). `exportSystem()`/`importSystem()` are unrelated — server-side, via `GET /api/v1/system-export` and `POST /api/v1/system-import`; `importSystem()` is the one `confirm()` left in the app, since it's genuinely irreversible. `initSystemImportButton()` reloads the page on success if nothing's dirty (same rule as restart detection), since the import can change `CONFIG_DIR`'s contents with no other way for the in-memory state to notice |

**`_expr` objects** (`{ _expr: "..." }`) are scalar fields toggled to raw Nix, or elements of package arrays. `isExprPkg(v)` distinguishes the two. `renderPkgArray` handles arrays at paths ending in `systemPackages`/`packages`/`extraPackages`/`extraPlugins`/`users.users.<name>.packages`.

**`renderEnumArray`** handles arrays whose option type parses as an enum (`parseEnumOptions`, e.g. `emulatedSystems`) — same chip-list UI as `renderPkgArray` but picking from the option's own enum values and appending plain strings.

**`_disabled` objects** are rendered by `renderDisabled`, which delegates to the normal renderer for the inner value and adds `is-disabled`. `isDisabled(v)` also guards `renderObj`/`renderTreeLevel` (disabled nodes render as tree leaves).

**`_commonMenuItems(path, { skipDisable })`** omits Disable/Rename for array-indexed paths (checked via `Array.isArray` on the parent, not by guessing from the segment's shape) — disabling/renaming a single array item isn't supported end-to-end (`json2nix.nix`'s `resolveExprs` only filters `_disabled` out of attrsets, and array items have no stable name).

**Autocomplete data**: `/autocomplete/{options,packages,kernels}.json`, served from `AUTOCOMPLETE_DIR` when set, else `autocomplete/` under WEBROOT.

**Rendering** is always a full re-render via `renderAll()` — no virtual DOM, no diffing.

## Terminal panel

xterm.js 6.0.0 + `@xterm/addon-fit` 0.11.0 + `@xterm/addon-webgl` 0.19.0, bundled locally in `webroot/addons/` (no CDN). WebGL loads opportunistically, falling back to Canvas 2D. UMD globals: `Terminal`, `FitAddon.FitAddon`, `WebglAddon.WebglAddon`.

Key constraints:
- `ResizeObserver` on `#term-output` is debounced 200ms so `fit()` only fires once the panel's CSS transition (180ms) settles.
- `fit()` is the only thing that triggers a PTY resize. `connectTerminalWs()`'s `onopen` calls it explicitly and sends `_term.cols`/`_term.rows` unconditionally (not `proposeDimensions()`, which is a pure calculation that can be stale right after a fast reconnect, and not gated on `onResize` firing, since a brand new server-side session — e.g. after `ezconf-terminal-session.service` restarts independently — has never been told any size at all).
- Never use a continuous `requestAnimationFrame` loop for rendering — on Linux without GPU acceleration it burns CPU proportional to canvas size.
- `--term-padding` (currently 2px) lives on `#term-output`, not on `.terminal.xterm` (xterm's own root element, a child `Terminal.open()` creates inside it, explicitly zeroed out) — despite `FitAddon.proposeDimensions()` reading `padding-*` from `.terminal.xterm` specifically when computing rows/cols, not from its parent, so `#term-output`'s padding is invisible to that calculation and the grid is sized for the full unpadded area, clipped by a few pixels at the bottom/right under `#term-output`'s own `overflow: hidden`. That mismatch is real, but negligible at this small a value — tried moving the padding to `.terminal.xterm` instead (which *does* get read by the fit calculation) and that produced visibly uneven padding in practice instead, for reasons not fully understood (likely xterm's internal canvas layers not respecting their own container's padding symmetrically) — reverted back to this approach as the better trade-off. Don't move it back to `.terminal.xterm` without re-verifying that actually looks right.

**CSS file roles**: `style.css` = layout, `theme-{nixos,dark,light}.css` = per-theme variables, `addons/xterm.css` = vendor file (unmodified).

The command-button bar sits below the terminal output, not above it — `.terminal-body` comes first in markup, and `.terminal-header`/`#terminal-header-install` are wrapped in `.terminal-header-group`, `position: absolute; bottom: 0` on `.terminal-panel` (itself `position: relative`) rather than plain flex children. That's deliberate, not just styling: as an ordinary flex child sharing the column with `.terminal-body`'s `flex: 1`, the header only ever sat at the bottom because the body above it was pushing it down — the instant `.terminal-panel.collapsed .terminal-body { display: none; }` removed that body from the flex calculation, the header snapped up to fill the vacated space instead of collapsing smoothly. Taking it out of flow entirely and pinning it to the panel's own bottom edge keeps it visually anchored there through the whole collapse/expand transition regardless of what the body is doing. `.terminal-body` carries a matching `padding-bottom` (33px, or 66px via `.terminal-panel.install-mode`) so its own content doesn't render underneath the now-overlaid header group. `.terminal-header`'s divider border is `border-top` (not `border-bottom`), matching the bar now sitting below rather than above.

**Theming rule**: any new customizable CSS value (colors, radii, sizes, spacing) must be a variable in all three theme files. Hard-coded values in `style.css` are only for structural properties that should never vary.

**Install mode** (`EZCONF_MODE`, set by `mode` in `ezconf.toml` / `services.ezconf.mode` in the NixOS module — deploy-time only, no CLI flag, no in-GUI toggle): a button with `mode = "install"` renders into a second row (`#terminal-cmd-btns-install`) instead of the ordinary one; that row is hidden unless `EZCONF_MODE === 'install'` (`INSTALL_MODE`). `renderButtons()` splits `getAllButtons()`'s result by `btn.mode` into two entry lists, each still indexed into the full list so `runButton()`/`showButtonMenu()` need no changes. The whole ordinary row (not each button) is disabled at once via a CSS class + `title` tooltip, both set once at init when `INSTALL_MODE` is true — the container-level `pointer-events: none` covers every button regardless of its own state, so `_updateDirty()`'s `save_first` toggle needs no install-mode awareness. The init code also adds `install-mode` to `#terminal-panel`, which a CSS rule bumps to `height: 66px` (collapsed) to fit both rows.

## Nix flake

`flake.nix` exposes four packages (`modules/ezconf-packages.nix`):
- `ezconf` — web server + assets; `--webroot` defaults to the Nix store share dir
- `ezconf-terminal` — `bin/terminal.py` as a standalone binary, separate derivation so asset changes don't restart the terminal service
- `ezconf-mkoptions` — `bin/generate-nixos-data.py` with nix + python-pam + cryptography in PATH
- `ezconf-mkcerts` — `mkcert`-based dev-cert helper

The `ezconf` derivation installs `webroot/` and `bin/server.py`. Autocomplete data is not installed — it's user-generated, belongs in a writable directory.

## NixOS module (`modules/ezconf.nix`)

Up to three systemd services under `services.ezconf.enable`:
- `ezconf.service` — restarts normally on rebuild (what restart-detection watches for)
- `ezconf-terminal.service` — only when `terminal = true`; `restartIfChanged = false` so sessions survive `nixos-rebuild switch`
- `ezconf-terminal-session.service` — only when `terminal = true` and `terminalPersist = true`; holds the actual shell (via dtach) in its own unit/cgroup, independent of the other two — see "Persistent sessions via dtach" above

Key options: `user`/`group` (default `root`), `https`/`generateCert`/`installCerts`/`cert`/`key`, `auth.{method,username,password,passwordFile,allowedUsers}`, `theme`, `mode` (see "Install mode"), `terminal`, `shell`, `terminalPersist` (default `false`, requires `dtach`), `nixosTarget`, `systemExportExcludeDotfiles`/`systemExportExclude`, `backupDir`/`backupCount`, `listen`/`interface`/`openFirewall`, `ports.{web,terminal}`, `configDir` (default `/etc/nixos/ezconf`, starts with **zero** tabs — see below), `defaultFile`, `trustedHosts` (`[ "*" ]` disables the CSRF Host check entirely), `buttons` (`{label, command, save_first, clear_first, menu, mode}` — every button shows regardless of which tab is active; `menu` groups same-named buttons into one dropdown, and nests further via "/" (e.g. `"Disk/Advanced"`) into a submenu inside that dropdown — see `_buildButtonMenuItems()`/the Context menu row above; `mode = "install"` moves a button into the install-only row).

**Why `configDir` starts empty**: an earlier version seeded `defaultFile` with `{}` on every activation if missing, which fought renaming/moving it directly — the next rebuild would silently recreate it, colliding with a later rename back to that name. `json2nix.nix`'s `lib.mkMerge` over zero files evaluates to `{}` fine, so an empty `configDir` is a valid, if inert, state — `renderEditor()`'s empty-state message offers New file/folder directly.
